# Performance and Profiling

The project is designed to make low-latency concepts measurable without pretending an ordinary Ubuntu/WSL2 UDP stack is exchange-grade kernel bypass.

## Benchmark

`feed_benchmark` runs a deterministic in-memory pipeline through encoder, decoder, and local book. It reports:

* total processing time,
* messages/sec,
* end-to-end p50/p95/p99/p99.9,
* dropped messages,
* detected sequence gaps,
* decoder errors.

The benchmark writes the required columns to `results/feed_benchmark.csv`. The repository ships only the header row initially; benchmark numbers are generated by execution rather than fabricated.

The benchmark's `transport` column is `in-memory`, so those results are not claims about UDP loopback performance.

## Latency timestamps

The live feed handler records:

* `source_timestamp_ns`: timestamp carried by the feed message;
* `receive_timestamp_ns`: monotonic Linux timestamp taken before decode;
* `decode_timestamp_ns`: monotonic timestamp after binary decoding;
* `processing_timestamp_ns`: monotonic timestamp immediately before the book update;
* `processing_end_timestamp_ns`: monotonic timestamp immediately after the book update.

Derived deltas are:

* `network_receive_delta = receive - source` when receive is not earlier;
* `decode_delta = decode - receive`;
* `processing_delta = processing_end - processing_start`;
* `end_to_end_delta = processing_end - source` when processing is not earlier.

In pipelined mode, `decode_delta` ends at the receiver thread's decode timestamp and therefore does not include time spent waiting behind the SPSC queue; the later processing timestamps separately expose queue-plus-book scheduling effects.

Because the simulator's source clock and the host's monotonic clock are not synchronized, `network_receive_delta` is meaningful only when the source timestamp is on a comparable clock. The project still records the field to show the boundary that a production design must solve with clock discipline.

`CLOCK_MONOTONIC_RAW` is used for local elapsed-time measurement because it is monotonic and not subject to wall-clock adjustments. A timestamp in nanoseconds describes the clock unit/resolution exposed by the API; it does not mean the OS, hardware clocksource, scheduler, or instrumentation is accurate to one nanosecond.

## Allocation behavior

The hot receive/decode path uses one reusable 64 KiB datagram buffer and fixed-size 48-byte message objects. The SPSC queue is preallocated. This avoids a heap allocation for every received message. The local order book uses `std::unordered_map` and `std::map`, so new orders and price levels can still allocate. That trade-off keeps the example understandable and testable on ordinary Linux.

Allocations matter in low-latency systems because allocator contention, page faults, cache misses, and fragmentation can introduce variability. Pointer-heavy containers also increase cache misses and pointer chasing. Production systems often use pools, arenas, flat arrays, intrusive data structures, or fixed-capacity hash tables where their workload permits.

## perf

```bash
perf stat -e cycles,instructions,branches,branch-misses,cache-misses,context-switches \
  ./build/feed_benchmark --messages 1000000

perf record -g ./build/feed_benchmark --messages 1000000
perf report
```

Use `perf` on a native Linux environment where kernel permissions permit it. WSL2 may expose a different subset of PMU data.

## strace

```bash
strace -f -tt -T -e trace=network,epoll_wait,epoll_ctl,read,write \
  ./build/feed_handler --port 9000 --mode single --count 1000
```

This is useful for observing system-call boundaries, but tracing itself changes timing and must not be treated as a low-latency benchmark.

## Likely bottlenecks

The first places to investigate are:

1. UDP system-call overhead and packet rate.
2. Datagram/message parsing branches and validation.
3. Map/hash allocations and cache misses in the order book.
4. Output/recording I/O if CSV or capture writing is enabled.
5. Queue backpressure in pipelined mode.
6. CPU scheduling and migration between threads.

A useful investigation cycle is to establish a baseline, capture `perf stat`, record a profile, make one change, rerun the same workload, and compare both throughput and tail latency.

## December evolution roadmap

A production-oriented extension path for December work is:

* multicast ingress and subscription management;
* `recvmmsg()` or similar batched receive to amortize system-call cost;
* CPU affinity and isolated receive/book cores;
* NUMA-aware placement of queues and memory;
* zero-copy or reduced-copy techniques where the transport API permits;
* flatter structures and better cache locality in the book;
* deeper lock-free pipeline decomposition only where measurement justifies it;
* a real DPDK transport adapter with mbuf lifecycle ownership;
* higher-throughput fixed-layout parsing, including vectorization only after profiling.

Each step should be benchmarked against a reproducible workload rather than adopted because it sounds faster.
